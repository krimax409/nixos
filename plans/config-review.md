# Ревью конфигурации NixOS

Отчёт по состоянию рабочего дерева на момент ревью. Конфигурационные файлы не
изменялись; этот файл содержит только найденные проблемы и рекомендации.

## Приоритеты

### P1 — Сборка не работает из Git-flake

**Файлы:** `modules/core/default.nix:3`, `secrets/infisical.yaml`

`secrets/infisical.yaml` находится в рабочем дереве, но не отслеживается Git.
При сборке через `.#desktop` или `.#laptop` Nix использует Git-источник flake и
не видит незатреканные файлы. Обе команды завершаются ошибкой:

```text
Path 'secrets/infisical.yaml' in the repository ... is not tracked by Git.
```

**Последствия:** полноценный `nixos-rebuild build` не запускается даже при
корректном содержимом секрета.

**Рекомендация:** добавить зашифрованный `secrets/infisical.yaml` и
`.sops.yaml` в репозиторий. Не добавлять расшифрованный файл и не обходить
проблему постоянным использованием локального `path:`-источника, если нужна
воспроизводимость.

### P1 — Общий SOPS-модуль сломан для laptop

**Файлы:** `flake.nix:57`, `modules/core/default.nix:4`,
`modules/core/default.nix:6`, `modules/core/default.nix:14`

Для laptop задан пользователь `krim`, но общий модуль SOPS жёстко использует:

- ключ `/home/k/.config/sops/age/keys.txt`;
- владельца секретов `k`.

На laptop ожидается `/home/krim`, а пользователя `k` конфигурация не создаёт.

**Последствия:** после устранения проблемы с незатреканным файлом laptop не
сможет расшифровать секреты с указанным ключом, а установка владельца может
завершиться ошибкой.

**Рекомендация:** передавать `username` в SOPS-настройки и строить путь/owner
от него либо использовать единый root-owned ключ в системном каталоге,
доступный только `sops-nix`.

### P1 — NOPASSWD allowlist даёт произвольное выполнение от root

**Файл:** `modules/core/sudo.nix:20`

Команды `nixos-rebuild`, `systemctl` и `git` разрешены без ограничения
аргументов. Кроме того, `modules/core/sudo.nix:44` выдаёт NOPASSWD-права всей
группе `wheel`, хотя `extraRules` ограничен конкретным пользователем.

**Последствия:** это не фиксированный allowlist. Например, unrestricted
`systemctl` позволяет связать и запустить пользовательский unit, а
unrestricted `nixos-rebuild` — применить внешний flake с произвольной
активацией. Любой пользователь из `wheel` получает те же беспарольные права.

**Рекомендация:** удалить широкое правило для `%wheel`, а для требуемых
операций использовать узкие root-wrapper’ы с фиксированными аргументами и
фиксированным flake-путём. Не разрешать напрямую общий `systemctl` или
`nixos-rebuild` без контроля параметров.

### P1 — Root-systemd запускает изменяемый пользователем скрипт

**Файл:** `modules/core/zapret.nix:22`

Системный unit запускает `/home/${username}/zapret-diy/zapret.sh` от root. Сам
скрипт и каталог находятся в домашнем каталоге пользователя и доступны ему на
запись. Тот же путь используется в `ExecStopPost` на
`modules/core/zapret.nix:23`.

**Последствия:** изменение скрипта пользователем приводит к выполнению
произвольного кода с root-правами при старте или остановке сервиса.

**Рекомендация:** собрать неизменяемый launcher через Nix в `/nix/store`.
Если динамическая часть обязательна, запускать её отдельным непривилегированным
процессом и выдавать только необходимые capabilities.

### P1 — Grok-конфигурация не переносима на laptop

**Файлы:** `modules/home/grok.nix:10`, `configs/grok/config.toml:5`,
`configs/grok/config.toml:16`, `configs/grok/config.toml:20`

`modules/home/grok.nix` подключается обоим хостам, но конфигурация содержит
жёсткие пути `/home/k`, включая команды получения токенов и путь к skill.

**Последствия:** на laptop с пользователем `krim` конфигурация будет указывать
на отсутствующие файлы и auth-команды. Сам Home Manager при этом может
успешно примениться, поэтому проблема обнаружится только при запуске Grok.

**Рекомендация:** сделать host/user-specific конфиги или генерировать TOML из
Nix с `${username}`. Для секретов оставить пути в `$HOME` либо использовать
поставляемые Home Manager wrapper’ы.

## Дополнительные риски

### P2 — Секреты экспортируются во все дочерние процессы shell

**Файл:** `modules/home/zsh/zsh.nix:102`

`INFISICAL_CLIENT_ID` и `INFISICAL_CLIENT_SECRET` экспортируются при каждом
запуске интерактивного zsh и наследуются всеми дочерними процессами.

**Последствия:** секрет может случайно попасть в окружение стороннего CLI,
debug-дамп, process inspection или удалённую команду.

**Рекомендация:** не экспортировать секрет глобально; использовать wrapper или
команду вида `infisical run -- <command>` только для потребителя секрета.

### P2 — Автоматический вход в пользовательскую сессию

**Файл:** `modules/core/niri.nix:64`

`greetd.initial_session` автоматически запускает Niri от имени основного
пользователя. Настроенный `tuigreet` используется только как fallback.

**Последствия:** при физическом доступе к включённой машине пароль пользователя
не требуется для входа в графическую сессию.

**Рекомендация:** оставить настройку только если автологин осознанно нужен.
Иначе убрать `initial_session` и использовать обычный login prompt.

### P2 — Глобально открытые порты без явных потребителей

**Файл:** `modules/core/network.nix:20`

На всех интерфейсах открыты TCP `80`, `443`, `59010`, `59011` и UDP `59010`,
`59011`. В конфигурации репозитория нет сервисов, которые явно используют
эти порты.

**Последствия:** будущий или внешний процесс, начавший слушать эти порты,
автоматически станет доступен из сети; на IPv6 это также может означать
публичную доступность.

**Рекомендация:** удалить неиспользуемые правила или ограничить их конкретными
интерфейсами и назначением.

## Несоответствия документации

### P3 — README расходится с конфигурацией

**Файлы:** `README.md:31`, `README.md:168`, `README.md:174`,
`hosts/laptop/default.nix:8`, `flake.nix:58`

- README сначала говорит, что виртуализация подключается только на desktop,
  но laptop тоже импортирует `virtualization.nix`.
- В разделе особенностей указано, что виртуализация включена на обеих машинах.
- README утверждает `24.05` для обоих state version, а laptop использует
  `25.11`.

**Рекомендация:** оставить одно фактическое описание и явно указать версии для
каждого хоста.

## Наблюдения по качеству

- `nix flake check --no-build --show-trace` проходит для `desktop` и `laptop`.
- Полная сборка обоих хостов блокируется только незатреканным
  `secrets/infisical.yaml`; после его добавления сборку нужно повторить.
- Все Nix-файлы проходят синтаксический parse.
- `python3 -m py_compile modules/core/hermes-discord-backup.py` проходит.
- `git diff --check` проходит.
- Установленный Hermes backup timer на desktop работает: последний проверенный
  запуск завершился `status=0/SUCCESS`.
- При `nix flake check` остаются предупреждения о legacy defaults GTK и Neovim;
  это не блокирует сборку, но их стоит обработать при плановом обновлении
  `home.stateVersion`.

## Рекомендуемый порядок исправления

1. Добавить зашифрованные SOPS-файлы в Git и повторить build обоих хостов.
2. Убрать hardcoded `/home/k` из общего SOPS/Grok-кода.
3. Пересобрать sudo-доступ через фиксированные wrapper’ы.
4. Убрать root-выполнение изменяемого файла из `/home` для zapret.
5. Решить, нужен ли автологин и глобальный экспорт Infisical-секретов.
6. Синхронизировать README с фактической конфигурацией.
